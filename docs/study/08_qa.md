# 8. 想定問答集

口頭試問で聞かれそうな質問と回答例です。**★ の付いた質問は全員が答えられるように** しておきましょう。

!!! tip "使い方"
    - まず質問だけを見て、**30 秒以内に自分の言葉で** 答えてみる。それから回答例を開いて比べる
    - 2 人 1 組で、片方が質問、もう片方が答える。答えたら「深掘り」の質問もしてみる
    - 回答例を丸暗記するより、**「なぜそうしたか」を自分の言葉で** 言えることが大事
    - 詰まった質問は、「参照」のページを読み直す

## A. 全体

??? question "★ Q1. このプロジェクトは何を作ったのですか？（30 秒で）"
    避難所や介護施設で、**複数台の小型 2 輪ロボットが隊列やフォーメーションで動くパフォーマンス** で人を楽しませ、物資の運搬もするシステムです。
    天井カメラで全ロボットの位置を測り、PC が隊形の目標を計算して各ロボットに速度を無線で指令し、各ロボットは車輪の速度を PI 制御で合わせます。
    PC 側は操作GUI・シミュレータ・ビジョンの 3 つのソフトで、すべて UDP 通信でつながっています。

    **参照**: [学習資料トップ](index.md#30-秒で説明する-coco-link)

??? question "★ Q2. システムの構成と、それぞれの役割を説明してください。"
    - **ロボット**（ESP32）: 指令された速度で車輪を回す下位制御。超音波・IMU・エンコーダ・LED・ブザーを持つ
    - **ビジョン**: 天井カメラでロボット（ArUco マーカー）の位置と向き、人（緑）・障害物（赤）・物資（青）の位置を測る
    - **操作GUI（上位制御）**: 全体の位置を見て各ロボットの速度を決める。モード選択、手動操作、システム同定、ログ記録
    - **シミュレータ**: 実機とカメラの代わりを、実機と同じ通信で演じる

    **深掘り**: 「それぞれの通信の頻度は？」→ 速度指令 20 Hz、ロボットのセンサ値 50 Hz、カメラ 30 Hz、ロボット内の制御 100 Hz。

    **参照**: [1. 全体像](01_overview.md)

??? question "★ Q3. なぜ上位制御（PC）と下位制御（ロボット）に分けたのですか？"
    車輪の速度制御は速い（100 Hz）制御が必要ですが、Wi-Fi 通信には遅れとばらつきがあり、**遅れのあるループで速い制御をすると不安定になりやすい** からです。
    そこで速い制御は遅れのないロボット内で、全体を見た判断は全ロボットの位置が分かる PC で行う **カスケード制御** にしました。
    PC が止まってもロボットは自分で止まれる、という安全面の利点もあります。

    **参照**: [2.12 安定性と遅れ](02_control_basics.md#212-安定性と遅れ)

??? question "Q4. なぜシミュレータを作ったのですか？ 何が工夫ですか？"
    実機が完成する前に上位制御を開発・テストするためです。工夫は、**シミュレータが実機とまったく同じ通信をする** ことです。
    操作GUIからは相手が実機かシミュレータか区別できないので、シミュレータで動いた制御が **プログラムを変えずに** 実機で動きます。
    さらに仮想ロボットに **1 台ずつ違う個体差** を持たせ、システム同定がそれを見抜けるか検証できるようにしました。

    **参照**: [1.2](01_overview.md#12-なぜシミュレータが実機と同じ通信をすることが大事か), [7.4](07_software.md#74-シミュレータと実機を同じにする設計)

??? question "Q5. シミュレータと実機の違い（シミュレータの限界）は何ですか？"
    シミュレータのモータは「一次遅れ＋不感帯＋電池電圧」のモデルで、車輪の **滑り**、床の凹凸、モータの発熱、超音波の反射の複雑さ、
    Wi-Fi のパケットロス、カメラのレンズ歪みや照明変化などは単純化しています。
    なので、シミュレータで動いたからといって実機で同じ精度が出るとは限らず、**実機でシステム同定と動作確認が必要** です。
    逆に、実機で同定した値をシミュレータに入れれば、シミュレータを実機に近づけられます。

??? question "★ Q6. 現在どこまでできていて、何ができていませんか？"
    - **できている**: 操作GUI・シミュレータ・ビジョンが動作し、フォーメーション・人追従・システム同定を **シミュレータ上で** 確認済み。自動テスト 127 個が Mac/Windows/Linux で通る
    - **ビジョン**: 合成画像で精度を確認（位置 1 cm、向き 3° 以内）。実カメラでは未検証
    - **できていない**: ロボットのファームウェアは **仕様書のみで未実装**。**実機での検証はこれから**

    「ファームウェアを仕様書どおりに作れば上位側はそのまま動く設計で、シミュレータの仮想ロボットがその手本（参照実装）になっている」と付け加えるとよい。

    **参照**: [1.5 現在の到達点](01_overview.md#15-現在の到達点正直に把握しておく)

## B. 制御の基礎

??? question "★ Q7. フィードバック制御とフィードフォワード制御の違いは？ COCO-LINK ではどう使っていますか？"
    - **フィードバック**: センサで測った実際の値と目標の差（偏差）から操作量を直す。外乱やモデルのずれに強いが、ずれが出てから直すので遅れる
    - **フィードフォワード**: モデルから必要な操作量を先回りして計算する。速いが、モデルがずれていると誤差が残る

    COCO-LINK の車輪制御は両方を組み合わせた **2 自由度制御** で、モータのモデルの逆（$u = (\omega^* + \tau\dot\omega^*)/K$）でほとんどを出し、残りの誤差を PI で直しています。

    **参照**: [2.7](02_control_basics.md#27-フィードフォワードと-2-自由度制御)

??? question "★ Q8. PID 制御の P・I・D それぞれの役割は？"
    - **P（比例）**: 今の偏差に比例して操作量を出す。P だけだと定常偏差が残る
    - **I（積分）**: 偏差を積算する。**定常偏差を 0 にする**。大きすぎると行き過ぎや振動
    - **D（微分）**: 偏差の変化の速さに比例。振動を抑えるがノイズを増幅する

    **深掘り**: 「なぜ P だけだと定常偏差が残るの？」→ 一定速度で回し続けるには一定の操作量が必要で、P 制御はそれを出すために偏差が残っている必要があるから。

    **参照**: [2.6](02_control_basics.md#26-pid-制御)

??? question "Q9. なぜ D 制御を使っていないのですか？"
    モータが一次遅れ系なので PI だけで十分速く安定にできることと、エンコーダの角速度は量子化ノイズを含むので、D 項がノイズを増幅してしまうからです。
    実際、IMC 法で設計すると一次遅れ系に対しては PI 制御器が自然に導かれます。

??? question "Q10. 積分ワインドアップとは？ どう対策しましたか？"
    操作量が上限で飽和している間も偏差が残るため、積分項が溜まり続ける現象です。目標に近づいても溜まった積分がなかなか減らず、大きく行き過ぎます。
    対策として、**出力が飽和している間は（さらに飽和を強める向きの）積分を止める** アンチワインドアップを入れています。

??? question "★ Q11. 一次遅れ系、ゲイン、時定数とは何ですか？"
    入力をステップ状に変えたとき、出力がすぐには変わらず指数関数的に近づく系です。伝達関数は $K/(\tau s + 1)$。
    **ゲイン $K$** は最終的にどれだけ出るか（定常値 ÷ 入力）、**時定数 $\tau$** は反応の速さで、**最終値の 63.2 % に達する時間** です。
    COCO-LINK のモータはこれでモデル化していて、公称値は $K$ = 25 rad/s/duty、$\tau$ = 60 ms（仮の値。実機では同定する）。

    **参照**: [2.4](02_control_basics.md#24-一次遅れ系ゲイン-k-と時定数-τ)

??? question "Q12. 2 自由度制御とは何ですか？"
    目標値への追従の仕方と、外乱への強さを **別々に設計できる** 制御構造です。COCO-LINK ではフィードフォワードで目標への追従を、フィードバック（PI）で外乱やモデル誤差の補正を担当させています。
    1 つのフィードバック制御器だけだと、目標への応答を速くしようとすると外乱への反応も同時に変わってしまいます。

??? question "Q13. ローパスフィルタを使っていますか？ 副作用は？"
    車輪の角速度はエンコーダ角の差分なのでガタガタしており、一次ローパス（$\alpha$ = 0.3, 100 Hz）で平滑化しています。
    副作用は約 23 ms の **遅れ** で、加速中に PI が「遅れている」と勘違いして押し過ぎ、約 15 % 行き過ぎていました。
    **目標値にも同じフィルタを通して遅れを揃える** ことで約 3 % に減らしました。

    **参照**: [3.5](03_robot_model.md#35-ロボットの中の車輪速度制御)

??? question "Q14. サンプリング周期はどう決めましたか？"
    ロボット内の制御はモータの時定数（約 60 ms）より十分速い 10 ms（100 Hz）にしました。1 時定数の間に 6 回測れます。
    外側の上位制御は 50 ms（20 Hz）で、内側ループより 5 倍遅くしています。カメラは 30 Hz です。

## C. システム同定

??? question "★ Q15. システム同定とは何ですか？"
    実際に動かして測ったデータから、制御対象のモデルのパラメータを求めることです。
    COCO-LINK では、モデルの形（一次遅れ＋不感帯）は物理から決め、値（$K, \tau, u_0$ など）を実験データから最小二乗法で求める **グレーボックス同定** をしています。

    **参照**: [4.1](04_system_identification.md#41-システム同定とは)

??? question "★ Q16. なぜシステム同定が必要なのですか？"
    1. 制御のゲインを勘ではなく **理論的に** 決めるため（モデルがあれば IMC 法で計算できる）
    2. 同じ部品でも 1 台ごとに特性が 5〜15 % 違うので、**ロボットごとに** 測ってゲインを合わせ、全台が同じように動くようにするため（隊形がそろう）
    3. シミュレータを実機に近づけるため

??? question "Q17. 何を、どんな実験で同定していますか？"
    | 実験 | 求めるもの |
    |---|---|
    | 3 秒静止 | ジャイロのバイアス |
    | duty をゆっくり増やす（その場旋回） | 不感帯 $u_0$ |
    | duty をステップ状に変える | ゲイン $K$、時定数 $\tau$ |
    | 前進・後退（カメラ使用） | 車輪半径 $r$ |
    | 左右に旋回（カメラ・ジャイロ使用） | トレッド幅 $b$ |
    | 速度ステップ | 検証（立ち上がり時間・オーバーシュート） |

    操作GUIのボタン 1 つで、約 55 秒で全部自動で行います。

??? question "★ Q18. 最小二乗法とは何ですか？"
    モデルの予測と測定データの **ずれ（残差）の二乗の合計が最小になるように** パラメータを決める方法です。
    二乗するのは、正負のずれが打ち消し合わないようにし、微分して解けるようにするためです。パラメータについて一次式なら、行列計算 $(A^\top A)^{-1}A^\top y$ で一発で解けます。

    **参照**: [4.3](04_system_identification.md#43-道具-1最小二乗法)

??? question "Q19. ARX モデルと非線形最小二乗法の違いは？"
    **ARX** は離散化したモデル $\omega_{k+1} = a\omega_k + b u_k$ の $a, b$ を線形の最小二乗法で求め、$K, \tau$ に戻します。簡単ですが、測定ノイズがあると偏りやすい。
    **非線形最小二乗法** は、$K, \tau$ でシミュレーションした応答と実測のずれを、繰り返し計算で直接最小にします。COCO-LINK は ARX の結果を初期値にして、非線形最小二乗で仕上げています。

??? question "Q20. 同定の精度はどうやって確かめましたか？"
    シミュレータの仮想ロボットに **答え（真のパラメータ）を隠して** おき、同定結果と比べました。個体差 ±15 % の条件で、
    $K$ 約 1 %、$\tau$ 約 3 %、不感帯 約 2〜3 %、車輪半径 約 0.2 %、トレッド幅 約 1 % の誤差でした。これは自動テストで毎回確認しています。
    実機では真値が分からないので、決定係数 $R^2$（モデルがデータをどれだけ説明できるか）と、最後の検証試験で評価します。

??? question "Q21. 同定で工夫した点、苦労した点は？"
    - **カメラとロボットの時刻合わせを不要にした**: 止まっている区間どうしの位置を比べるので、時刻が多少ずれても影響しない
    - **ロボットの時計を使う**: Wi-Fi の到着時刻はばらつくので、ロボットがセンサを読んだ時刻で微分・積分する
    - **時定数が 2 割小さく出る問題** を見つけた: 送信 50 Hz・制御 100 Hz だと 1 サンプルの間に入力が 2 回変わることがあり、入力と応答の対応がずれていた。同定中だけ 100 Hz に上げて解決
    - フィルタの遅れを避けるため、角速度ではなくエンコーダ角の差分を使う

    **参照**: [4.7](04_system_identification.md#47-実験設計の工夫ここが説明できると強い)

??? question "Q22. 同定結果からどうやって PI ゲインを決めましたか？"
    **IMC（内部モデル制御）法** です。閉ループを時定数 $\lambda$ の一次遅れ $1/(\lambda s + 1)$ にしたいと決めると、
    制御対象 $K/(\tau s+1)$ に対して PI ゲインは $k_p = \tau/(K\lambda)$、$k_i = 1/(K\lambda)$ と計算できます。
    PI 制御器のゼロでモータの遅れ（極）を打ち消すイメージです。$\lambda$ が唯一の調整つまみで、既定は 50 ms。
    フィードフォワードも $k_{ff} = 1/K$、$\tau_{ff} = \tau$ と同定値から決まります。

    **参照**: [4.8](04_system_identification.md#48-同定結果から制御器を設計するimc-法)

## D. 上位制御

??? question "★ Q23. 非ホロノミック拘束とは何ですか？ なぜ問題になるのですか？"
    速度に対する制約で、2 輪ロボットは **自分の向いている方向にしか進めず、真横には動けない** ことです。
    そのため「目標との差に比例して速度を出す」単純な方法が使えず、向きを変えながら近づく専用の制御則（極座標フィードバックや Pure Pursuit）が必要になります。

    **参照**: [3.3](03_robot_model.md#33-非ホロノミック拘束横には動けない)

??? question "Q24. ロボットを目標の位置と向きに止める制御は？"
    **極座標フィードバック** です。目標までの距離 $\rho$、目標の方向へのずれ $\alpha$、最終的な向きのずれ $\beta$ を使って
    $v = k_\rho\rho$、$\omega = k_\alpha\alpha + k_\beta\beta$ とします。ゲインの符号の条件を満たせば目標に収束することが知られています。
    目標が後ろなら後退する、向きが合うまで前進を弱める、などの工夫もしています。

??? question "★ Q25. フォーメーションはどういう仕組みですか？"
    **仮想構造法** で、隊形全体を 1 枚の見えない板とみなし、その上に席（スロット）を並べます。板の中心を動かしたり回したりすると隊形ごと動きます。
    どのロボットがどの席に行くかを **ハンガリアン法** で移動距離の二乗和が最小になるように決め、各ロボットは自分の席へ極座標フィードバックで向かいます。
    近くの他のロボットは減速・回避します。

    **参照**: [5.2](05_upper_control.md#52-フォーメーション)

??? question "Q26. ハンガリアン法とは？ なぜ距離の「二乗」の和を最小にするのですか？"
    $n$ 台のロボットを $n$ 個の席に割り当てる組合せ（$n!$ 通り）の中から、コストの合計が最小の割り当てを $O(n^3)$ で求めるアルゴリズムです。
    二乗和を最小にすると、**ロボットの直線経路が交差しない** 割り当てになることが知られており、衝突しにくくなります。

??? question "★ Q27. 人追従（隊列）はどういう仕組みですか？"
    人の通った道を点列（パンくず）として記録し、先頭ロボットはその道を、人から道のりで 40 cm 後ろを保ってたどります。
    2 台目は 1 台目の道を、3 台目は 2 台目の道を 25 cm 間隔でたどります。人が障害物を避けて歩けば、ロボットも同じ道で避けられます。
    速さは道のりの差に比例（P 制御）、曲がり方は **Pure Pursuit** で決めます。

    **参照**: [5.3](05_upper_control.md#53-人追従隊列)

??? question "Q28. Pure Pursuit とは？ 調整するパラメータは？"
    道の上で一定距離（注視距離）先の点を目標にし、その点を通る円弧に乗るように曲がる方法です。曲率 $\kappa = 2\sin\alpha/L_d$、$\omega = v\kappa$。
    注視距離 $L_d$ が小さいと正確に沿うがふらつき、大きいと滑らかだが内側を回る、というトレードオフがあります（既定 12 cm）。

??? question "★ Q29. 安全対策は何をしていますか？"
    - **ロボット側**: 指令が 300 ms 来なければ自分で止まる **ウォッチドッグ**、解除まで動かない **E-STOP**、低電圧で停止
    - **PC 側**: 進行方向の超音波が 30 cm 以下で減速・8 cm で停止、ロボット同士の回避、**E-STOP ＞ 手動 ＞ 同定 ＞ モード** の優先順位
    - PC が止まってもロボット単体で止まれるよう、最後の砦はロボット側に置いた多重構造です

??? question "Q30. 通信が切れたり、PC が固まったりしたらどうなりますか？"
    ロボットは指令が 300 ms 届かないと、自分でモータを止めて待機状態になります（ウォッチドッグ）。
    操作GUIは 2 秒間何も届かないロボットを「切断」と表示し、ロボットは 1 秒ごとに `hello` を送り続けるので、通信が戻れば自動で再接続されます。
    操作GUIの制御は画面と別のスレッドで動いているので、画面が重くなっても制御は止まりません。

## E. ビジョン

??? question "★ Q31. ロボットの位置はどうやって測っていますか？"
    天井カメラでロボット上面の **ArUco マーカー** を検出し、マーカーの 4 隅から中心（位置）と上辺の向き（ロボットの向き）を求めます。
    画像の座標（ピクセル）は、**ホモグラフィ** で床の座標（メートル）に変換します。ホモグラフィはフィールドの四隅に置いたマーカーから自動で計算します。

    **参照**: [6. ビジョン](06_vision.md)

??? question "Q32. ホモグラフィとは？ なぜ 4 点必要なのですか？"
    平面上の点を別の平面に移す射影変換で、床が平面なら画像座標と床座標は 3×3 の行列 1 つで変換できます。
    行列の 9 要素のうち全体の倍率は自由なので未知数は 8 個、1 組の点の対応で式が 2 本立つので、4 組の対応で決まります。

??? question "Q33. 視差補正とは？"
    マーカーは床から約 8 cm 高い位置にあるので、床面のホモグラフィで変換すると、カメラ真下から外側にずれて見えます。
    相似な三角形から、カメラ真下からの距離を $(H-h)/H$ 倍して補正します（$H$: カメラの高さ, $h$: マーカーの高さ）。
    カメラ高さ 2 m、真下から 1.5 m の位置では 6 cm もずれるので、補正は必須です。

??? question "Q34. 色の認識に HSV を使ったのはなぜですか？"
    RGB だと明るさが変わると 3 つの値すべてが変わりますが、HSV では色の種類が **色相 H** だけで表されるので、照明の変化に強いからです。
    H・S・V の範囲で二値化し、ノイズを除去して、床の上での面積が小さいものは捨て、重心を位置としています。
    ロボットの LED を人と間違えないよう、ロボットの周りは除外しています。

??? question "Q35. カメラの遅れにはどう対処していますか？"
    撮影から届くまで 50〜100 ms 遅れるので、その間に進んだ分を、エンコーダから求めた速度で計算して足しています（遅延補償）。
    カメラにロボットが一瞬映らなかったときも、0.5 秒までは車輪の回転から位置を推測（推測航法）し、それ以上なら「位置不明」として制御から外します。

## F. ソフトウェア

??? question "Q36. なぜ TCP ではなく UDP にしたのですか？"
    速度指令や位置は **最新の値だけが大事** で、1 秒に 20〜50 回送るので、1 回落ちても次がすぐ来ます。
    TCP は届くまで再送するので、古いデータの再送待ちで遅れが出ることがあり、制御には向きません。
    万一ずっと届かなくなっても、ロボットのウォッチドッグで止まるので安全です。

??? question "Q37. なぜ ROS を使わなかったのですか？ 代わりにどうしましたか？"
    プロジェクトの要件として使わないことになっていました。代わりに、通信の決まり（メッセージの種類・中身・ポート番号・周期）を
    **プロトコル仕様書** として自分たちで設計し、PC とロボットの共通の「契約」にしました。
    ログの記録には ROS 系でも使われる MCAP 形式を使い、Foxglove などの既存ツールで見られるようにしています。

??? question "Q38. プログラムが正しいことはどうやって確認していますか？"
    **自動テストを 127 個** 作り、GitHub に送るたびに Mac・Windows・Linux で自動実行（CI）しています。
    通信の往復、ファームウェアの安全機能、フォーメーションの収束、システム同定の精度、合成画像での位置推定精度などを確認しています。

??? question "Q39. チーム開発でどう工夫しましたか？"
    Git で機能ごとにブランチを分けて開発し、プルリクエストで CI が通ったことを確認してから本流に入れています。
    また、PC とファームウェアの間の通信仕様とファームウェア仕様書を文書化し、別の人が作っても組み合わさるようにしています。

??? question "Q40. 新しい動作（例：協調物資運搬）を追加するにはどうしますか？"
    モードは **プラグイン** になっていて、決まった形のクラスを 1 ファイル書いて `modes/` に置くだけで、操作GUIに自動で出てきます。
    物資運搬なら、物資（青）を囲む隊形を作り、物資の中心を隊形の中心として目標地点へ動かす、という設計を考えています（`docs/adding_a_mode.md`）。

## G. 今後・自分たち

??? question "★ Q41. 実機ではどうやって検証するつもりですか？"
    1. ファームウェア仕様書の **受入試験チェックリスト**（センサの向き・ウォッチドッグ・E-STOP など）を確認
    2. 操作GUIの **手動操作** で前後左右に動くか確認
    3. **システム同定** で各ロボットの特性を測り、ゲインを書き込んで、検証試験で立ち上がり時間やオーバーシュートを確認
    4. フォーメーション・人追従を実行し、**MCAP ログ** から隊形の誤差や追従間隔を数値で評価

??? question "Q43. 一番苦労したこと・面白かったことは？（例）"

    テレメトリと制御の周期のずれが原因だと分かり、同定中だけ送信周期を上げて解決しました。
    もう 1 つは、検証試験で見つけた速度制御のオーバーシュートを、フィルタの遅れを揃える工夫で 15 % から 3 % に減らせたことです。
